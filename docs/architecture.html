Architecture

Walkthrough: from inputs to final output

One run of /sprint-zero, in the order it happens. The ten numbered steps are the ten boxes along the pipeline in the figure.

Inputs

  • A reference URL, the product you want something similar to, and optionally a repo URL to reverse-engineer alongside it. If you type /sprint-zero with nothing after it, the session asks for a project name and these URLs first.
  • One scoping reply, a paragraph answering six questions: build level, core loop, project type, stack, data layer and anything to exclude. Whatever you skip gets the default (MVP, web-app, node-react, local) and is logged as an assumption.
  • Optional flags: --fresh deletes docs/ and regenerates the specs, --rebuild deletes the code directories and rebuilds, --no-launch stops before starting the app, and --present opens the presenter UI and takes the scoping reply from its form.

Before step 1

The main session reads .sprint-zero/status.json if a previous run left one and prints where it is resuming from. With --present it also installs, builds and starts the presenter in the background, reads the port from .sprint-zero/presenter.json and opens it in the browser.

The ten steps

  1. Scope. The session asks the six-part scoping question once, fills any gap with a default, and writes the answers down. With --present it waits up to 15 minutes for the presenter's form to write the same file instead. If the data layer is supabase, it then checks .env for the four Supabase keys and waits until they are there.

    Reads the URLs, your reply, stacks.md · Writes docs/scope.md · If it fails SCOPE_NEEDED

  2. Research. The session studies the reference with web search and fetch: what the product does, its features, its pricing tiers, the repo's README and folder layout if a repo was given, and a targeted look at the core loop. It stops rather than invent anything if the site or repo is unreachable.

    Reads scope.md, the public web · Writes docs/reference-brief.md · If it fails DISCOVERY_NEEDED

  3. PRD. The session describes the product to build, not the reference. The core loop is the spine, excludes become non-goals, and sign up, log in, log out and session persistence are always must-haves for anything with users. The build level sets how demanding the acceptance criteria are.

    Reads scope.md, reference-brief.md · Writes docs/prd.md · If it fails SPEC_INCOMPLETE

  4. Decisions. The session walks the reference's feature list and records, in plain language, each feature that was simplified, dropped or deliberately excluded, plus the technical choices actually made: stack, data layer, project type and testing approach.

    Reads scope.md, reference-brief.md, prd.md · Writes docs/decisions.md · If it fails SPEC_INCOMPLETE

  5. User stories. Every must-have and should-have story is expanded with Given/When/Then acceptance criteria concrete enough for a browser test to verify, a priority and an effort estimate. The auth stories are added if the PRD missed any.

    Reads scope.md, prd.md · Writes docs/user-stories.md · If it fails SPEC_INCOMPLETE

  6. API contract. The session lists every entity and endpoint the stories need, marks which are protected, and fixes the auth model and base URL from the build configuration. For a cli-tool the contract describes commands, arguments and output instead of HTTP endpoints. From here on this file is law.

    Reads scope.md, stacks.md, prd.md, user-stories.md · Writes docs/api-contract.md · If it fails SPEC_INCOMPLETE

  7. Build brief. The first hand-off. The session spawns tech-lead, which can only read. It resolves the build configuration against the catalog into concrete directories, ports and run commands, says which engineers to spawn and in what order, and flags any missing or malformed doc. The brief is printed so you can read it before any code is written.

    Reads scope.md, prd.md, api-contract.md, decisions.md, stacks.md · Returns the build brief (no file) · If it fails BUILD_BRIEF_NEEDED

  8. Build. The session spawns backend-engineer and, for a web-app, frontend-engineer in the same turn. The backend engineer builds the API (or the CLI), the data access, the auth endpoints and a seed script with realistic demo data. The frontend engineer builds login, signup, session handling, protected routes and the product screens. Neither talks to the other; both build to the contract. The session waits for each one's exact completion message and marks it done in the status file.

    Reads the spec set, stacks.md · Writes server/ and client/ (or one app/, or cli/) · If it fails BUILD_NEEDED

  9. QA. Once the engineers are done, the session spawns qa-engineer with the resolved ports. For a web app it checks both sides against the contract, runs API integration tests, then drives a real browser through the auth dance (signup, session, logout, login, protected route, 401) and the core loop. An API service gets the API checks only; a CLI is run with sample arguments. Prod adds an error-path test per loop; clickable skips auth and API tests. The session turns the report into the delivery summary.

    Reads the spec set, the running build · Writes tests under server/tests/ · Returns the pass/fail report · If it fails QA_NEEDED

  10. Launch. Unless --no-launch was passed or QA said the build is not ready to demo, the session installs any missing dependencies, runs the seed script and captures the demo login it prints, starts the backend and frontend in the background, checks each answers over HTTP, and opens the app in your browser.

    Reads scope.md, stacks.md · Writes the seeded database, the final status.json with phase: done · If it fails LAUNCH_FAILED (the build itself still stands)

Final output

  • A spec set of six files in docs/: scope, reference brief, PRD, decisions, user stories and API contract.
  • A working build in server/ and client/ for the default configuration, with a seeded SQLite database and QA's tests alongside it.
  • A delivery summary in the terminal: project, scope level, core loop, pass or fail for backend, frontend and the auth dance, test counts, known issues, and a yes or no on "ready to demo".
  • A running app opened in your browser, with the backend and frontend URLs, the demo email and password, and the commands to stop the servers. With --present the same result appears in the presenter UI.

If a run stops partway

A step that fails unrecoverably prints its named state with a recovery instruction and stops, so a broken spec never reaches the build. Running /sprint-zero again resumes: spec steps whose file exists are skipped, engineers already marked done in status.json are not re-spawned, and anything that was still running when the session broke is run again.
