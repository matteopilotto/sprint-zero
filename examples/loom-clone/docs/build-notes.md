# Build notes

What earlier batches learned about this build. Every engineer and QA sub-agent reads this file before working on a refinement.

## House rules

Standing instructions from the user about how this build may be worked on. They override the agents' defaults.

- No browser automation. Do not launch, open, or drive any browser: no Playwright, no puppeteer, no headless Chrome or Brave, no `open`. Say so in every sub-agent brief. Reason: an earlier agent's headless test launches coincided with the user's Brave crashing. (2026-11-26)
- The user tests by hand, in Brave. Never use Chrome. (2026-11-26)
- Do not stop processes you did not start. If a server needs restarting and it is not yours, ask. (2026-11-26)
- Use the exact labels in `docs/user-stories.md`. The user tests against them. (2026-11-26)

## Constraints

Facts about how this build works that no spec file holds, added by the engineers who found them.

- **Worker ticker for anything drawn into the recording.** The recorder tab is usually in the background while recording, where the browser slows `requestAnimationFrame` down. Anything drawn into the recording must be driven by the worker ticker, not `requestAnimationFrame`, and times must come from timestamps, not tick counts. File: `client/src/recorder/tickWorker.js`. [baseline]
- **Nothing is loaded from outside localhost at runtime.** No CDN scripts, fonts, or models. The person-detection files are copied from `node_modules` into `client/public/mediapipe/` on `predev` and `prebuild`. File: `client/scripts/copy-mediapipe.mjs`. [baseline]
- **Camera view controls are page-only.** "Dim", "Hide", and "Camera view size" are done with DOM and CSS over the displayed camera view. They must never touch the canvas or the stream that feeds the recording. File: `client/src/components/CameraView.jsx`. [02, 03]
- **Click order for the floating window.** `documentPictureInPicture.requestWindow()` only works straight from a user click and uses that click up. In `handleStart` it is called after `getDisplayMedia()` has been called and before anything is awaited. Keep that order. File: `client/src/pages/RecordPage.jsx`. [07]
- **The floating window closes for an entire-screen share.** A page cannot hide one of its own windows from a capture of the entire screen, so the window is closed before recording starts, using the `wholeScreen` value. Files: `client/src/recorder/useRecorder.js`, `client/src/recorder/useFloatingWindow.js`. [07]
- **Recording starts 250 ms after the countdown leaves the screen.** The recorder waits in a phase named `starting` so the screen has repainted before the first frame is captured. Starting in the same instant puts the countdown's "1" in the video. File: `client/src/recorder/useRecorder.js`. [05]
- **Media keys need a playing sound.** The browser only sends Play/Pause and Next track to a page that is playing something, so a silent looping sound holds the media session for the length of the take. File: `client/src/recorder/mediaKeys.js`. [08]
- **Camera size and data rate rules live in one file.** The camera opens at 640x480 in "Screen + camera" and follows "Video quality" in "Camera only" (1280x720 or 1920x1080), capped at 1280x720 while "Blur" or "Custom image" is on. The camera reopens when the size changes, which is only allowed in the setup phase. Video is H.264 in MP4 at every quality and in every mode, at a data rate set from the picture size; the MP4 types are in `mp4MimeTypes`. Only on the WebM fallback is video VP9 at "720p" and "1080p" with no camera effect and VP8 otherwise. File: `client/src/recorder/quality.js`. [09, corrected in 10]
- **A take is held in browser memory until "Stop".** Very long recordings are a risk. File: `client/src/recorder/useRecorder.js`. [baseline]
- **Integration tests use contract values as "invalid" examples.** When a contract value changes, check whether an existing test used it as its invalid example. The suite had 120 checks as of batch 1. File: `server/tests/integration.test.js`. [02]
- **Capture cannot be checked without a browser.** Everything about capture, the camera, person detection, playback, and download can only be confirmed by the user in a browser. Report it as untested, never as passing. [baseline]
- **A recording's file ending comes from its `mime_type`, and no column stores it.** `video/mp4` is `<id>.mp4` and anything else is `<id>.webm`. Always get the path from `storedFilePath(row)` and delete with `removeFiles(id)`; do not build the path by hand. Files saved before batch 4 are `<id>.webm` whatever their type, so `storedFilePath` tries the other ending when the expected file is missing. File: `server/lib/helpers.js`. [10]
- **The upload's ending is only known after the whole file is on disk.** A browser sends the codec list with a comma in the part's content type, which the upload parser reports as `text/plain`, so the file is first written under a guessed ending and `keepUpload` renames it once the type has been read from the file's first bytes. Keep the `keepUpload` call before the database insert. The integration suite had 126 checks as of batch 4. Files: `server/lib/upload.js`, `server/routes/recordings.js`. [10]
- **The MP4 is made in two steps, and naming a data rate forces re-encoding.** The browser's recorder is asked for MP4 (H.264 and AAC) first; after "Stop" the take is rewritten by `mediabunny` into an ordinary MP4 with its index at the start, copying sound and picture as they are. In that rewrite, passing `bitrate` or `quality` for a track makes `mediabunny` re-encode it, so they are only passed for a track that is not already H.264 or AAC. Files: `client/src/recorder/toMp4.js`, `client/src/recorder/useRecorder.js`. [10]
- **WebM is the fallback at three points.** The recorder falls back to WebM if the browser will not record MP4, or if the MP4 recorder reports an error before producing any data. A WebM take is then re-encoded to MP4 in the browser after "Stop" (slow for long takes), and only if that also fails is it uploaded as WebM. The upload filename and the "Download instead" filename both come from the blob's type, so keep the blob type exactly `video/mp4` or `video/webm`. Files: `client/src/recorder/useRecorder.js`, `client/src/recorder/toMp4.js`, `client/src/api/client.js`. [10]
- **A grid thumbnail is a live `<video>`, not a picture.** Each card in the "Grid" view holds a muted `<video preload="metadata">` pointed at `GET /recordings/:id/file` with `#t=0.1` on the end of the address; that fragment is what makes the browser draw a frame without playing, so keep it. Every card on the page opens its own video and asks the server for the start of the file, and nothing is cached as an image, so a very large library costs one media element per recording. File: `client/src/components/RecordingThumbnail.jsx`. [12]
- **The library view is kept under its own storage key.** "List" or "Grid" is saved in `localStorage` as `loomclone_library_view`, separate from the recorder's `loomclone_recorder_settings`; anything other than `grid` reads as "List". File: `client/src/pages/LibraryPage.jsx`. [12]
- **The three recording icons are drawn in one component and named twice.** "Rename", "Download", and "Delete" are inline SVGs in `RecordingActions`, shared by the "List" rows, the "Grid" cards, and the recording page; no icon library or font is used. Each control carries its name as both `title` (the hover text) and `aria-label` (what a screen reader says), so a change of name must be made in both. "Download" is a link, not a button. File: `client/src/components/RecordingActions.jsx`. [14]
- **The grid card's age and length are worked out in the browser when the card is drawn.** `formatAge` counts a month as 30 days and a year as 365, and does not tick: the age is as of the last time the library was drawn. `formatLength` writes a whole number of hours as "1 hr", with no "0 min". The "List" view and the recording page keep `formatDuration` and `formatDate`. File: `client/src/format.js`. [15]
- **A grid card has no padding of its own.** `.recording-card` sets the shared `.card` padding to 0 so the thumbnail reaches the edges; the text and icons are padded by `.recording-card-body`. The card does not clip its contents, so the thumbnail rounds its own top corners at 11px (the card's 12px less its 1px border). File: `client/src/styles.css`. [15]
